# Store service state in PostgreSQL

Tana and the collector each store their state in their own PostgreSQL database, owned by a role of the same name, so each service controls its schema while sharing a database server. A connection pool lets feed processing, downloads, metadata workers, and status queries proceed concurrently; proxy workers under [ADR 0012](0012-independent-metadata-proxy-workers.md) claim from the same queues as the main fetcher. Pool sizes are configured per service; the collector's default is larger because it runs more concurrent workers. The collector's dataset of roughly 9 GB, mostly retained metadata and catalog projections, can be inspected with `psql` and exported with `pg_dump` while the service runs.

Transactions run at READ COMMITTED, so read-then-write sequences lock what they depend on explicitly. Queue claims select rows with `FOR UPDATE SKIP LOCKED` and transition them only from the expected state, letting concurrent workers take different jobs but never the same one. Singleton settings and state rows are locked before conditional updates. Ban deadlines from [ADR 0008](0008-panda-ban-groups.md) are written with `GREATEST`, so concurrent ban responses can only extend a deadline; only an explicit reset under [ADR 0017](0017-explicit-panda-ban-reset.md) shortens one.

Times are `TIMESTAMPTZ` and an unset time is NULL, so ordering, interval arithmetic and null checks happen in SQL and `psql` shows readable values; flags are `BOOLEAN`. Each service embeds its migrations and applies them at startup inside a transaction holding an advisory lock, so concurrent starts apply each version once; a database newer than the binary is refused. Files such as reference import inputs stay in the data directory.
